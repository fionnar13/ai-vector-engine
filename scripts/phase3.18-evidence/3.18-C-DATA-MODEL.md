## C1. SemanticCorrectionTarget

### Full JSDoc typedef

```js
/**
 * @typedef {Object} SemanticCorrectionTarget
 * @property {string} id
 *   Content-derived 'sct-<8-hex>' = 'sct-' + fnv1a32(stableStringify({
 *     objectId, currentRole, targetRole, source
 *   })). Deterministic and stable: the same deviation re-derived in a later
 *   iteration yields the SAME id (iteration is deliberately NOT an input —
 *   the attempt transaction, not the target, is the per-iteration record).
 * @property {string} objectId
 *   The corrected object's id, copied VERBATIM from the upstream record
 *   (deviation.objectId / expectation record objectId). Never re-derived,
 *   never remapped.
 * @property {string} currentRole
 *   The ACTUAL role at derivation time (the deviation's `actual` / the
 *   provider-observed role). MUST be in T20's 7-role emission vocabulary
 *   (semantic-inference.js:152-155; guard per normalizeProposal :229-231).
 * @property {string} targetRole
 *   The EXPECTED role (the deviation's `expected` / the agenda record's
 *   role). Same vocabulary + guard.
 * @property {number|null} confidence
 *   Verbatim-or-null copy of the upstream belief (the semanticResults entry
 *   confidence — evaluation.js:1287/:1289 — or the agenda record's
 *   confidence). NO fabrication: never synthesized, never clamped, never
 *   defaulted. null when upstream has none.
 * @property {ReadonlyArray<{signal: string, description: string, weight: number}>} evidence
 *   Frozen CLONE of the upstream evidence rows (cloneData pattern,
 *   semantic-inference.js:196-204/:236); defaults [] when upstream has none.
 *   Provenance only — never executed, never validated against stores.
 * @property {string} source
 *   Deterministic pointer to WHERE the target came from, in house id space:
 *   'dev-<8-hex>' when derived from a semantic deviation (engine path), or
 *   'smr-<8-hex>' when derived directly from an agenda expectation record
 *   (host path). Exactly one upstream record exists per target; `source`
 *   names it without holding a reference to it.
 */
```

### ID derivation

- Prefix: **'sct-'** (semantic-correction-target) — new member of the house prefix family,
  constructed exactly like the existing ones via the contentId shape
  (correction.js:628-630).
- Inputs: `{objectId, currentRole, targetRole, source}` — the correction INSTANCE identity.
- Deliberately EXCLUDED from the hash: `confidence` and `evidence` (belief data). Design
  decision (disclosed, C9 #3): the id names WHICH correction (object + pair + origin), so
  a re-derivation that refreshes belief data keeps the same targetId — the correction
  session tracks ONE target across iterations, and downstream records (diagnosis,
  proposal) reference it stably. Contrast: the critic proposal includes `confidence` in
  its id (critic.js:262-265) because a critic proposal IS its full content; the target is
  a session-stable handle. Both conventions are content-derived and deterministic; the
  difference is intentional and documented.
- Worked example: see §C6 (Golden Scenario: `sct-86f52be0`).

### Design notes

- `currentRole`/`targetRole` are checked against the frozen 7-role vocabulary at
  construction (the normalizeProposal guard pattern, semantic-inference.js:229-231); the
  same 7 are the evaluation-side twin SEMANTIC_EMITTABLE_ROLES (evaluation.js:1252). No
  alias surface exists in the engine (B11 #1 of Checkpoint B: zero 'title' anywhere), so
  no alias handling is defined.
- The §22 `evidence` property (spec proposes `Object`) is narrowed to the frozen evidence
  ROW ARRAY (the T20 evidence shape {signal, description, weight} — semantic.js:135 etc.,
  normalized verbatim at semantic-inference.js:236). An object-shaped free-for-all would
  break content-addressing and freeze discipline; the array is what actually flows
  upstream. Disclosed as a typed refinement of the §22 sketch, not a change of meaning.
- `confidence` provenance: for the engine path it is the VIOLATED semanticResults entry's
  confidence (evaluation.js:1313 — the EXPECTED side's belief, verbatim-or-null); for the
  host path, the agenda record's confidence. Both are the same upstream field by
  construction (records ARE the agenda entries, A2 pin).

### Non-canonical proof (C5 applies)

- No key maps to ObjectStore/GeometryStore/AppearanceStore/SceneGraph/SemanticStore:
  `objectId` is a pointer STRING into the document, not document data; roles are
  derivation vocabulary; confidence/evidence are upstream BELIEF snapshots; `source` is
  an id string. The typedef holds no geometry params, no appearance stack, no node, no
  semantic record body.
- No mutable reference: constructed by clone + deep-freeze (the createDeviation pattern,
  evaluation.js:459-479; cloneData, semantic-inference.js:196-204); evidence is a frozen
  copy, never an aliased upstream array.
- No execution surface: no execute/commit/write; nothing in the typedef is callable; the
  plain-data scan (findFunctionPath, evaluation.js:452-453) applies at construction.
- Cannot bypass Transaction: the target names a desired ROLE, which is DERIVED state
  (D-10, Checkpoint B §B4.5) — there is nothing in it a transaction could "apply" directly.

### Static registry description

- `SEMANTIC_CORRECTION_CAPABILITIES` (proposed name): a module-level
  `deepFreeze([...])` array with EXACTLY ONE entry — the shape⇄background
  capability above. Frozen AND enumerable (array iteration/filter is the
  lookup; house pattern: CORRECTION_CAPABILITY_RECIPES, correction.js:1328-1347,
  a frozen array filtered at :1389). No map, no registry class, no mutation path.
- Capability matching (selector design): (1) role-pair match —
  (currentRole, targetRole) positionally in (sourceRoles, targetRoles);
  (2) precondition match — the target's object facts (geometry type, node
  childCount, world bbox area) satisfy `preconditions`. BOTH must hold for
  CORRECTABLE; this makes the B10 footnote rows (* non-rect → background,
  container-override) first-class refusal outcomes instead of hidden failures.

### Design notes

- STATIC description, not a runtime record: no objectId, no confidence, no
  evidence, no timestamps. It describes WHAT the engine can do, in principle,
  once — the same content every time. This is the 3.18 mirror of the recipe
  table's static side (correction.js:1328-1347) at the semantic layer.
- `risk: 'MEDIUM'` is a vocabulary-conformance choice, not a judgment call
  imported from outside: the house already prices T06-based correction at
  MEDIUM (:1332/:1334) and the ranking consumes it via CORRECTION_RISK_WEIGHT
  (correction.js:1364) — a semantic capability riding the same tool MUST use
  the same vocabulary and the same value, or the priority arithmetic
  (:1514-1523) would compare incommensurable numbers if semantic strategies
  ever join ranking.
- `deterministic: true` mirrors the T06 tool flag (tools.js:328) and the
  command-level `deterministic: tool.deterministic === true`
  (correction.js:2424); `reversible: true` mirrors every existing recipe
  (:1330-1346 all reversible:true) and is backed by the B8 snapshot-inverse
  proof, not asserted.

### Non-canonical proof (C5 applies)

- Pure module constant: no store keys, no object ids, no document data at all
  (thresholds are ENGINE CONSTANTS from semantic.js:167/:172 — they describe
  the derivation, they do not store document state).
- Fully frozen (deepFreeze at module level, :1328 house pattern); arrays frozen;
  no callable properties.
- No execution surface: the capability cannot transform anything — it is the
  DESCRIPTOR a later checkpoint's selector reads; execution authority remains
  TransactionBuilder/Executor exclusively (B7).
- No aliasing: it aliases nothing — it is constructed once, in code, from
  literals.

## C3. SemanticCorrectionDiagnosis

### Full JSDoc typedef

```js
/**
 * @typedef {Object} SemanticCorrectionDiagnosis
 * @property {string} targetId
 *   The 'sct-<8-hex>' SemanticCorrectionTarget id (C1). NOT the 'ctarget-'
 *   id of the §7 CorrectionTarget (correction.js:772) — different id space,
 *   different layer.
 * @property {'CORRECTABLE'|'UNSUPPORTED_TRANSITION'|'NO_CAPABILITY'} status
 *   The three-value verdict (see vocabulary below).
 * @property {string|null} capabilityId
 *   'cap-shape-background' IFF status === 'CORRECTABLE'; null otherwise.
 *   A non-null capabilityId on a non-CORRECTABLE diagnosis is a
 *   construction breach.
 * @property {string|null} reason
 *   Deterministic machine string (SCREAMING_SNAKE, the
 *   'EXPECTED_ROLE_UNSUPPORTED' style — evaluation.js:1289-1305); null when
 *   CORRECTABLE (the compared-pair reason:null convention, evaluation.js
 *   :1310/:1313).
 * @property {ReadonlyArray<string>} affectedObjectIds
 *   Frozen plain array of object ids whose derivation the correction touches.
 *   For the ONE capability: exactly [target.objectId] (scope LOCAL — the
 *   mutation is confined to the target object; T06 touches nothing else,
 *   tools.js:335-342).
 */
```

### Status vocabulary + the mandatory distinction

| Status | Meaning (layer) | When it fires | reason |
|---|---|---|---|
| CORRECTABLE | semantic capability layer | role pair matches a registry capability positionally AND all preconditions hold for the target's object facts | null |
| UNSUPPORTED_TRANSITION | semantic capability layer — STATIC verdict (B4 pin, NEW 3.18 vocabulary) | roles are valid T20 roles but NO capability applies to this (currentRole, targetRole) pair as narrowed by preconditions | 'ROLE_PAIR_UNSUPPORTED' (generic pair), 'GEOMETRY_TYPE_NOT_ELIGIBLE' (rect-gate (a) violated), 'CONTAINER_OVERRIDE_WOULD_INTERCEPT' (constraint (b) violated), 'STRICT_CROSSING_UNACHIEVABLE' (constraint (c) margin unachievable for this instance) |
| NO_CAPABILITY | correction ENGINE terminal (EXISTING record, correction.js:1397-1404) | ONLY when MIRRORING the engine's resolution outcome — the 6-key record {status, targetId, category, rootCause, metric, objectIds} remains the engine's sole output; this layer references it, never redefines or re-derives it | 'ENGINE_RESOLUTION_NO_CAPABILITY' |

The B-approved distinction is preserved verbatim: UNSUPPORTED_TRANSITION is the static,
pre-strategy, pre-transaction capability-selector verdict (names the TRANSITION as the
impossible thing); NO_CAPABILITY is the engine's terminal record for zero-recipe
resolution (:1390-1404; leads to TERMINATED/'UNFIXABLE' per :2981-2987/:3000-3018). They
are NOT aliased: different layers, different producers, different downstream behavior.
Out-of-vocabulary roles NEVER reach this layer — the evaluation arm already refuses them
(UNSUPPORTED/EXPECTED_ROLE_UNSUPPORTED, evaluation.js:1288-1291), so the diagnosis
vocabulary needs no fourth value for them.

### Design notes

- **This is NOT the existing correction.js CorrectionDiagnosis.** The existing engine
  diagnosis (createCorrectionDiagnosis; content keys :822 = {targetId, rootCause,
  confidence, affectedObjects, recommendedStrategies}; wrapped as {status:'RESOLVED',
  diagnosis} at :1415-1422) carries STRATEGIES for the executor and its targetId names a
  'ctarget-' §7 target (correction.js:772). The SemanticCorrectionDiagnosis is the
  SEMANTIC-layer verdict: different keys (status/capabilityId/reason/affectedObjectIds),
  different id space (sct-), different producer (the capability selector, pre-strategy),
  different consumer (the 3.18 wiring that decides whether to build a proposal at all).
  Both records continue to exist; neither replaces or reshapes the other. The engine
  diagnosis is produced only for targets that REACH engine resolution; the semantic
  diagnosis is produced for every semantic deviation target, BEFORE any strategy exists.
- `affectedObjectIds` for the ONE capability is always exactly the target object
  (single-object, scope LOCAL). The frozen-array discipline matches the house records
  (plainCopy + deepFreeze at construction, e.g. correction.js:765/:772).
- Determinism: same deviation + same object facts + same registry → same diagnosis,
  same reason, byte-identical record (no RNG, no wall-clock — house record discipline,
  evaluation.js:444-447 header).

### Non-canonical proof (C5 applies)

- No store mapping: object ids are pointer strings; status/reason are vocabulary;
  capabilityId is a static descriptor id. No geometry/appearance/node/semantic bodies.
- No mutable reference: clone + deep-freeze construction (house pattern);
  affectedObjectIds a frozen COPY (never the upstream array).
- No execution surface: a diagnosis proposes nothing and executes nothing; the refusal
  statuses in particular terminate thought, not transactions.
- Cannot bypass Transaction: it commands no tool; CORRECTABLE merely AUTHORIZES a later
  checkpoint to build a proposal (which is itself inert, C4).

### Mutation descriptor (T06 uniform-scale form)

```js
/**
 * @typedef {Object} SemanticCorrectionMutation
 * @property {'transform'} kind — prompt-pinned value ('transform'); kind is
 *   INERT at execution (correctionCommandFor binds by toolId, :2418, and
 *   carries kind verbatim :2421-2422). Vocabulary layering disclosed in C9 #1.

 *   transform with ALL SIX numeric keys, det = a*d - b*c, |det| >= 1e-12.
 *   The MATRIX FORM is constrained by the capability's matrixForm
 *   'UNIFORM_SCALE': b === 0, c === 0, a === d === s, with
 *   tx = cx*(1-s), ty = cy*(1-s) for the chosen fixed point (cx, cy) —
 *   NO shear (B5(d)). s is computed from the CURRENT world area A and the
```

post-mutation rect x=-29.128784747791997, y=35.435607626104, width=458.257569495584,

with the 5% margin, verified by computation (scripts/phase3.18-c-hashes.mjs, checks all

### Design notes

- **A proposal is NOT a transaction.** It is inert frozen data with zero
  execution surface. Execution authority belongs exclusively to
  TransactionBuilder/TransactionExecutor (B7: one atx- transaction per attempt,
  built by the correction layer, committed by the substrate). The proposal's
  `mutation.input` is the CANDIDATE input a later checkpoint's plan derivation
  may carry into a command descriptor (the correctionCommandFor binding,
  correction.js:2417-2459) — until then it transforms nothing.
- `expectedSemanticEffect` MUST NOT claim success: it carries `toward`, never
  `to`/`result`/`guaranteed`; the house effect vocabulary is directional
  expectation ('TOWARD_TARGET', correction.js:1374-1378), and verification is
  RE-DERIVATION after commit (B9 §B9.5-6), never read off the proposal.
- `predictedWorldArea` is the selector's arithmetic prediction (matrix |det| ×
  current world area, under the host's world-transform obligations, B5);
  it exists so the strict-inequality precondition is CHECKABLE at construction
  time (C8) — it is still only a prediction.
- `confidence` is copied from the target (which copied it from upstream) — the
  proposal ADDS no belief of its own. No fabrication anywhere in the chain:
  deviation (no confidence) -> semanticResults entry (verbatim-or-null,
  evaluation.js:1287) -> target (verbatim-or-null) -> proposal (verbatim-or-null).

### Non-canonical proof (C5 applies)

- No store mapping: objectIds are pointer strings; the transform is CANDIDATE
  tool input (numbers), not document state; expectedSemanticEffect is
  vocabulary + a predicted number; provenance is id strings + frozen evidence
  rows.
- No mutable reference: clone + deep-freeze construction throughout (house
  pattern; the JSON-clone+freeze precedent for nested intent data is
  createCorrectionProposal's intent handling, critic.js:254).
- No execution surface: no execute/commit/apply; the only "action" it names
  (toolId T06 + input) is DATA describing a candidate command.
- Cannot bypass Transaction: T06 writes reach stores ONLY through the executor
  pipeline (tools.js:195-224 substrate wrapper; correction.js:2546); a frozen
  descriptor outside that pipeline is inert by construction. The direct-role-
  write door stays shut (D-10, B4.5) — the proposal carries no role-write
  semantics at all.

## C9. Discrepancies

1. **kind vocabulary layering (design note, not a code contradiction).** The prompt pins

2. **C2 property-list extension (disclosed).** Spec §16's 9 properties are kept verbatim;
